# 创新点清单（视频/文档/答辩三处复用）

> 使用方法：每个创新点给了「一句话卖点」（讲给评委的第一句）+ 技术依据 + 演示画面 + 评委可能的追问和答法。
> 排序即建议的强调顺序。答辩/文档里只主打前 4 条，后 2 条作为储备，贪多会稀释。

---

## 1. 混合检索 RAG：稀疏 + 稠密双路召回，LLM 语义重排

**一句话卖点**：绝大多数参赛作品把大模型当"问答机器"，我们让它建立在可溯源的领域知识库上——而且是三种检索策略里实测效果最好的一种。

- 技术依据：BM25 稀疏召回（关键词精确命中）与 DashScope text-embedding-v3 稠密向量（语义近义召回）经 RRF 融合，再由大模型对候选片段语义重排并剔除不相关内容；回答附带站内引用来源可跳转原文。
- 演示画面：茶道AI 问「新手喝什么茶不容易失眠」，展示流式回答 + 点击引用卡跳原文。
- 评委追问「为什么不用现成的 RAG 框架？」→ 答：检索融合与重排逻辑需要与站内业务数据（商品/讲座/资讯）深度耦合，自研流水线约 600 行，换来对每个环节的可控与可测（见创新点 2）。
- 评委追问「为什么不直接微调模型？」→ 答：茶文化知识更新频繁（上新商品、活动），向量库增量更新成本远低于微调；且微调模型无法提供引用溯源。

## 2. 检索质量可评测：40 题评测集 + 三策略消融

**一句话卖点**：我们不靠感觉调 prompt——检索质量用 Recall@3 和 MRR 摆在表里，随时可复跑。

- 技术依据：内置 40 题茶文化评测集与标注答案，管理端一键运行三种检索策略（纯 BM25 / 混合 / 混合+重排）的消融对比；`GET /ai/status` 暴露当前检索架构自检。
- 演示画面：管理台「RAG 评测」页，快速验证（前 8 题）跑完出对比表。
- 评委追问「40 条语料是不是太少？」→ 坦诚回答：当前为演示规模，架构按增量设计，扩容语料无需改代码（见文档展望）；评测集与语料同源也是已知限制，下一步计划引入独立题集。
- （这条的坦诚回答反而是加分项：说明团队理解评测方法论，而不是刷分。）

## 3. ReAct Agent 业务闭环：AI 决策直接驱动业务动作

**一句话卖点**：别的作品 AI 只能"聊"，我们的 AI 能查订单、挑商品、直接把推荐结果加进购物车。

- 技术依据：自研轻量工具调用循环（最多 4 轮），工具含查订单/推荐商品/检索知识/泡茶指南/推荐讲座；模型自主规划调用次数与检索词改写；前端时间线可视化「思考→调用→结果」。
- 演示画面：「我上次买的龙井怎么样？再推荐一款类似的」→ 时间线展示先查订单再推荐 → 推荐卡片直接加购。
- 评委追问「如何防止 Agent 乱调用？」→ 答：工具白名单 + 参数由服务端校验 + 轮数上限，不存在自由 SQL 或自由下单。
- 评委追问「多模态在其中扮演什么角色？」→ 答：图片输入会并入 Agent 的上下文，同一套决策链路处理"看图提问"，见创新点 4。

## 4. 自然语言查数：让运营不写 SQL

**一句话卖点**：中文提问直接出统计图——但接口只开放四种白名单统计，大模型负责"听懂"，不负责"碰数据库"。

- 技术依据：LLM 意图解析（sales_by_product / click_by_product / order_status / sales_by_category 四类白名单）→ 服务端执行受限 SQL → 条形图渲染；解析失败有关键词兜底，不会白屏。
- 演示画面：管理台「自然语言查数」页连续问两个示例问题。
- 评委追问「NL2SQL 的注入风险？」→ 答：模型输出被约束为四类枚举意图而非 SQL 文本，SQL 由服务端模板拼接，参数化传值——这是与"直接让模型生成 SQL"的方案的本质区别。

## 5. 离线演示模式（评审环境友好）

无 API Key / 无外网时自动降级：BM25 检索 + 本地推荐，功能链路不中断。答辩时可以现场演示"拔网线也能跑"，非常直观地回应"现场没网怎么办"的经典问题。

## 6. 全站统一的设计系统「夜茶·墨绿金」

前台与管理端共用一套色板（墨绿 #08130d + 金 #D4AF37 + 米白 #EDE6D6）与同一份衬线题字字体（思源宋体 Heavy 子集），管理端不依赖 Node 工具链即可部署（纯静态页 + classpath 自动映射），从 URL 到视觉都是"一个作品"而非"两个项目拼接"。

## 使用禁忌

- 不要说"填补空白""国内领先"——评委反感；说"在我们的检索评测里""相对纯 BM25 基线提升 X%"。
- 所有数字必须与管理端实测一致，说不准就现场跑。
- 被指出弱点时先承认再给计划，不要硬拗。
